# Content plan — next 60 cheat sheets

This document is the content backlog for the catalog. It ranks the next sixty sheets by relevance, and gives the writing agent a short brief per sheet so each one lands at the catalog's quality bar on the first pass.

The ranking blends four signals, in this order of weight:

1. **Daily use.** The owner's working stack: TypeScript, React/Next.js, .NET/C#, Python, AWS, Cloudflare, PostgreSQL, Kafka/MQTT, IoT and renewable-energy systems, and Claude Code.
2. **Market demand in 2026.** Stack Overflow Developer Survey 2026, GitHub Octoverse 2026, State of JS/React 2025, DORA 2025, LinkedIn Skills on the Rise 2026, WEF Future of Jobs 2025, and job-posting analyses (see [Sources](#sources)).
3. **Catalog gap.** The `career` section is empty; `data`, `infrastructure`, `cloudflare` and `practices` hold one or two sheets each; there is no testing, CSS, accessibility, auth, observability, IaC or shell sheet at all.
4. **Fit for the medium.** A Kindle sheet pays off for material a reader returns to, not for news. Topics that change monthly are either scoped to their stable core or kept on the watch list.

## Universal brief for the writing agent

Every row below assumes this. Do not repeat it per sheet; do not skip it.

- **Load the `writing-cheatsheets` skill first** and follow it literally: `## Mental model` first, 4–9 topic sections each opening with a 2–6 row table, one callout per section at most, `## Further reading` last, code lines ≤ 52 characters, constrained Markdown only, no MDX.
- **Your training data is stale for 2026.** Do not write any version number, limit, quota, default, deadline or "latest release" from memory. Fetch the primary source on the day you write, pin `topicVersion`, and list the pages you read in `verifiedAgainst`. The [stale-recall hazards](#stale-recall-hazards-for-the-writer) list below names the traps already known.
- **Run every sample.** `ts` blocks are type-checked by `npm run verify:samples`; run `bash`, `sql`, `py` and `cs` samples yourself before committing. Cloud-service sheets (`aws`, `cloudflare`) are the exception: tag samples `js`/`bash`/`json`, syntax-check them, and verify claims against provider docs instead.
- **One sheet, one topic.** Each brief names what is out of scope. Link to the sibling sheet instead of re-explaining it, and set `related` accordingly.
- **Write for a human on a 6.8″ grayscale screen.** Terse, second person, present tense, no hedging, no filler, no meaning carried by color. The reader is a working engineer who knows the topic exists and wants the detail that bites.
- **The gotcha test.** A callout earns its place only if a competent engineer actually makes that mistake. Prefer `Gotcha:`. Never invent one to fill the slot.
- **Finish with the gate:** `npm run lint` at zero errors, `npm run pdf:dev -- <slug>`, open both PDFs, walk the checklist in `references/quality-checklist.md`. Set `lastVerified` only after that.
- **Slugs are permanent.** Use the slug in the table exactly; it is printed in every PDF footer and QR code.
